## What Route A changes (and does not)

**Files:**
- **Notebook:** `arcaid3/part3/notebook/arcaid3-lexicon-view.ipynb`. It has 23 cells: the 19 original cells with unchanged source, plus 4 added.
- **Kaggle settings:** `arcaid3/part3/notebook/kernel-metadata.json`, with the same datasets, model, docker image and RTX PRO 6000 as the 4.17 run.
- **The added code cell:** `arcaid3/part3/lexicon_view_cell.py`, generated by `build.py` from `lexicon_view_template.py`, with `arcaid3/part2/lexicon.py` embedded word for word.

**What the cell does:**
1. Adds four read-only members to the sandbox's `FrameView`, plus a small helper namespace. The lexicon runs in its own namespace, so its names cannot clash with the sandbox's.
2. Appends **one sentence** to the system prompt. That is about 60 tokens per request.
3. Runs a **self-test through the real sandbox** before the games start. If anything fails, it **restores the stock sandbox** and the run continues exactly as the base would.
4. Wraps the sandbox call with an **observe-only counter**: how many tool calls read the new view.

**Unchanged:** model, serving, KV cache, images, the other prompts, actions, schedule and time budget.

**Kill switch:** `ARCAID3_LEXICON=0`.

## How to judge it honestly (this is the part that usually goes wrong)

Part I measured how noisy one draw is: the same code has scored 5.68, 4.09 and 2.30.

**1. Check the mechanism first, on the save run, before spending a submission.**
- `ARCAID3_LEXICON_READY` appears near the start of the log.
- `ARCAID3_LEXICON_STATS` / `ARCAID3_LEXICON_FINAL` show `calls_using_view` above about 5% of `tool_calls`.
- **If the model almost never reads the view, the change is inert.** Stop, rather than sampling noise on the leaderboard. This is exactly what happened to `arc3_stall`, whose warnings never reached the model (`submissions/ANALYSIS-2026-09-26.md`).
- No new sandbox errors, timeouts or out-of-memory lines compared with the 4.17 log.

**2. Then compare draws, not a draw.**
- Alternate days between the unchanged base and Route A.
- After 5 or more draws each, compare the means.
- With a per-draw spread around 0.35–0.5, 5 per arm can only show a difference of about 0.6 or more. 10 per arm gets to about 0.4.

**3. Falsifiers.** Route A is dropped if any of these holds:
- `calls_using_view` is under 5% of tool calls;
- error, timeout or out-of-memory counts rise;
- after 5 or more draws per arm, the Route A mean is not above the base mean.

**4. Final selection (2 allowed).** Pick on mean over several draws, not on the single best draw.

## Route C: the plain alternative if ARCAID3 is not the goal

If the only goal were leaderboard score, the evidence says:
- port a cross-game scheduler, or adopt a larger-memory serving stack, from the published Milestone 2 notebooks (Part I §5);
- do not add any prompt or memory module.

ARCAID3's view is independent of those, so it can be added on top of either later.

## What a good outcome would and would not show

- **A good outcome:** the model reads the view often, and Route A's mean over several draws is above the base's. That would be the first leaderboard evidence that *giving a model more ways to look at the same screen* helps on unseen games, which is the central bet of ARCAID3.
- **What it would not show:** that the lexicon is the best view, or that it works for every game. The per-game results in Part II already show it is worse than Duck's own view on some games. That is why it is offered *alongside* Duck's view, not instead of it.
